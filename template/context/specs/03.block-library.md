# Spec 03 — Rebuild the Block Library Around Categories and Variations

**Priority:** P3  
**Depends on:** Spec 02

## Problem

`components/blocks/` currently mixes real reusable presentation sections with provider-aware components, forms, editors, application workspaces, and other logic-bearing concepts.

Known examples that require reclassification include:

```text
auth-forms.tsx
clerk-auth.tsx
contact-editor.tsx
campaign-editor.tsx
task-editor.tsx
ai-playground.tsx
settings-page.tsx
social-composer.tsx
application-workspace.tsx
```

A block that owns state, Clerk behavior, RHF behavior, persisted data, provider logic, or business orchestration is not a pure block.

## Required outcome

Create a reusable BoldKit-like catalog organized by presentation category, with multiple variations per category where useful.

## Canonical block rules

A block:

- composes UI primitives;
- accepts typed props/slots;
- remains presentation-only;
- does not fetch or mutate persisted data;
- does not authenticate or authorize;
- does not call provider SDKs;
- does not own business workflows;
- does not own React Hook Form state.

## Required category direction

Normalize toward files such as:

```text
hero-sections.tsx
cta-sections.tsx
feature-sections.tsx
stats-sections.tsx
faq-sections.tsx
testimonial-sections.tsx
pricing-sections.tsx
data-tables.tsx
record-details.tsx
dashboard-sections.tsx
kanban-boards.tsx
calendar-sections.tsx
timeline-sections.tsx
invoice-sections.tsx
onboarding-sections.tsx
settings-sections.tsx
empty-states.tsx
error-states.tsx
audit-sections.tsx
file-sections.tsx
```

Only create a category when current application surfaces genuinely need it.

## Grouped variation rule

"Grouped" means more than a one-component file renamed to plural.

Example:

```text
hero-sections.tsx
  HeroCentered
  HeroSplit
  HeroWithStats
  HeroMinimal
```

Use meaningful variations that can be selected by Loaded Vibes later.

Do not create artificial variants solely to meet a count.

## Reclassification rules

### `auth-forms.tsx`

Delete/reclassify. Auth forms belong in `features/auth/` as RHF feature forms.

### `clerk-auth.tsx`

Delete/reclassify. Clerk-aware behavior belongs in auth features/integration boundaries, not generic blocks.

### Domain editors

`contact-editor`, `campaign-editor`, `task-editor`, `invoice-editor`, social composer, and similar logic-bearing editors become feature forms/client features using UI primitives and/or pure display blocks as appropriate.

### Application workspaces

If a component is pure structural presentation, extract a generic category block with typed props.

If it owns application state/orchestration, move it to the relevant feature.

## Naming

Block filenames:

```text
lowercase-kebab-case.tsx
```

Exports:

```text
PascalCase descriptive variation names
```

## Duplication policy

Prefer a small amount of clear local variation over a generic "mega block" with dozens of conditional modes.

Extract only stable repeated presentation concepts.

## Acceptance criteria

- [ ] `components/blocks` contains presentation categories, not provider/domain-service buckets.
- [ ] Active grouped category files contain genuinely useful named variations.
- [ ] No block imports Prisma, fetchers, actions, auth server helpers, authz, provider SDKs, or workflows.
- [ ] No block owns RHF or equivalent form state.
- [ ] `auth-forms.tsx` and `clerk-auth.tsx` are removed or reclassified.
- [ ] Domain editors/composers are moved to features where required.
- [ ] Existing useful hero/CTA/FAQ/stats/team/testimonial/etc. work is preserved or normalized rather than discarded blindly.
- [ ] Block naming follows lowercase kebab-case.
- [ ] Blocks inherit the dark-only design system from primitives.
- [ ] Relevant type/lint/build checks pass.
