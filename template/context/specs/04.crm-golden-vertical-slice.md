# Spec 04 — Normalize CRM Contacts as the Golden Vertical Slice

**Priority:** P4  
**Depends on:** Spec 03

## Goal

Make CRM contacts the canonical reference implementation for the Maximal Template domain/resource architecture.

Do not refactor every recipe at once.

Once CRM contacts is correct, later work can replicate the same grammar across Projects, Support, Invoicing, Marketing, Social, AI, Portal, and Admin where applicable.

## Required route family

```text
/crm/contacts
/crm/contacts/new
/crm/contacts/[contactId]
/crm/contacts/[contactId]/edit
```

## Required feature family

Use clear responsibility names equivalent to:

```text
contactsFeature.tsx
contactsClientFeature.tsx
contactDetailFeature.tsx
contactDetailClientFeature.tsx   # only if browser interaction exists
contactNewForm.tsx
contactEditForm.tsx
contactsSkeleton.tsx
contactDetailSkeleton.tsx
```

Do not create a client companion that has no browser-only reason to exist.

## List feature

The list route must:

- render a server feature;
- read contacts through `crmFetchers`;
- use explicit safe list criteria;
- use a data-table block;
- isolate browser search/filter/sort/selection behavior into a narrow client feature when needed;
- preserve tenant/resource scope for real protected reads;
- render seeded/demo data safely for the signed-out public demo as designed.

## Detail feature

The detail route must:

- resolve/validate `contactId`;
- use the canonical CRM fetcher;
- render a record-detail block;
- return the appropriate not-found behavior for missing/inaccessible real data;
- avoid Prisma in the route/feature.

## New form

`contactNewForm.tsx` must:

- be a React Hook Form feature;
- compose UI primitives directly;
- use the canonical CRM Zod schema;
- call the create CRM action;
- display validation/action errors;
- never require a `ContactEditorBlock`.

## Edit form

`contactEditForm.tsx` must:

- be a React Hook Form feature;
- load its initial DTO through the server route/feature boundary;
- compose primitives directly;
- use the canonical edit schema;
- call the update action;
- handle stale/missing/inaccessible records safely.

## Fetchers

Normalize CRM persisted reads under a domain file such as:

```text
lib/fetchers/crmFetchers.ts
```

Required contact read shapes include equivalents of:

```text
getContacts
getContactById
```

Additional scoped helpers may exist only when they represent a real read contract.

Fetchers are read-only.

## Actions

Normalize CRM writes under:

```text
lib/actions/crmActions.ts
```

Required contact CRUD operations include equivalents of:

```text
createContact
updateContact
deleteContact or archiveContact
```

Actions authenticate/authorize/validate and perform the ordinary CRUD write.

Non-CRUD CRM calculations/automation do not belong here.

## Schemas

Create/use:

```text
schemas/crmSchemas.ts
```

Include only schemas required by current CRM boundaries.

Avoid one giant `mutations.schema.ts`.

## Types

Create/use:

```text
types/crmTypes.ts
```

Include useful shared CRM transport/form contracts.

Do not mirror every Prisma model mechanically.

## Selects / DTOs

Use domain-appropriate select and DTO helpers under:

```text
lib/db/selects/
lib/db/dto/
```

The selected persistence shape should contain only what the feature needs.

DTOs crossing into client/presentation code must be serializable.

## Auth/authz

Real contact writes must demonstrate:

- authenticated user;
- active local identity;
- tenant membership;
- CRM capability;
- resource ownership/assignment policy where applicable;
- RLS containment.

The public demo may render safe seeded/read-only state signed out without converting production authorization into anonymous authorization.

## RLS

The contacts table/query path must preserve organization/tenant containment.

RLS tests or equivalent real-boundary evidence should be used when such repository tests exist or are added as part of the actual RLS implementation.

Do not claim RLS proof from UI behavior alone.

## Suspense

List/detail pages should use Suspense with contact-specific skeletons where the persisted read is streamed.

## Cache

Any persistent cache must preserve tenant scope and freshness requirements.

Do not cache authorization truth or sensitive mutable contact state without explicit proof.

## Acceptance criteria

- [ ] All four contact routes exist.
- [ ] Pages are thin.
- [ ] List/detail server features do not import Prisma/provider SDKs.
- [ ] Browser filtering/search is isolated when required.
- [ ] New/edit forms are RHF features that import primitives directly.
- [ ] No contact form block exists solely to preserve the normal feature→block rule.
- [ ] All contact persisted reads use `crmFetchers`.
- [ ] All ordinary contact CRUD writes use `crmActions`.
- [ ] CRM schemas/types are domain-organized.
- [ ] Select/DTO boundaries are explicit where needed.
- [ ] Real writes authenticate/authorize before mutation.
- [ ] Tenant/RLS scope is preserved.
- [ ] Public signed-out demo browsing remains available.
- [ ] Suspense/skeleton behavior is implemented where appropriate.
- [ ] This slice is documented by implementation shape clearly enough to be copied by later domain normalization.
