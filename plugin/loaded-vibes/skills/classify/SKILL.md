# /classify: one answer, from the doctrine

Read `${CLAUDE_PLUGIN_ROOT}/references/doctrine.md` first. Its classifier and rule table are the only source; never answer from memory and never invent a layer or directory.

## Method

1. Restate the work as one responsibility. If it is two (a read and a write, a form and its action), classify each part separately.
2. Walk the classifier top to bottom; the first "yes" is the home. Static public presentation and forms are checked before features on purpose.
3. Name the domain: the owning module id (`hipster.modules.json`) or the new domain id from `context/docs/Architecture.md` §6. Base code (no module) uses the base names the classifier shows.
4. Build the file name from the classifier pattern: `<d>` is the domain in camelCase, `<Thing>` and `<Verb>` in PascalCase, transactions in kebab case (`<d>-<verb>-<noun>.tx.ts`). Prefer an existing file of that layer for the domain (append to `lib/actions/<d>Actions.ts`) over a new one. In `features/<d>/` the slice naming wins over the raw pattern, whether or not the folder exists yet: `<things>Feature.tsx` (list), `<thing>Feature.tsx` (detail), `<thing>NewForm.tsx` (create form), `<thing>EditFeature.tsx`, `<thing>Skeleton.tsx`, `<things>Feature.client.tsx`.
   Types versus mapping: DTO, command and other shared _types_ are `types/<d>Types.ts`; `lib/db/dto/<d>.dto.ts` holds only the record → DTO functions and `lib/db/selects/<d>.selects.ts` the select objects with their payload types.
5. Pick the rules: every row of the rule table whose layer matches, plus the `any` rows that the work touches (naming, server-only, formatting). Add CC-MOD-001 when the code sits in a module and imports another module.
6. If nothing matches, the answer is "Stop" with CC-NAME-002, and a question for the owner. Do not propose a new folder, a `services/`, `utils/<domain>/` or similar.

## Answer format

Reply with exactly this block per part, nothing else unless asked:

```text
path:   lib/actions/shopActions.ts (append)
layer:  action (Ordinary CRUD write)
why:    a "use server" mutation boundary: auth → authz → Zod → tenant write → ActionResult
rules:  CC-WRITE-001, CC-WRITE-002, CC-WRITE-003, CC-SRV-001, CC-NAME-001
```

`path` is relative to the app root and says `(new)` or `(append)`. `rules` lists IDs only; the owner can look them up in the table.

## Examples

From an app with a `shop` module (entities `order`, `product`):

| Ask                                                | Path                                                               |
| -------------------------------------------------- | ------------------------------------------------------------------ |
| "Orders list as a page"                            | `app/(tenant)/orders/page.tsx` + `features/shop/ordersFeature.tsx` |
| "Form to create a product"                         | `features/shop/productNewForm.tsx` (new)                           |
| "Only the order's creator may cancel it"           | `lib/authz/policies.ts` (append)                                   |
| "Refund an order and restock its products at once" | `lib/db/transactions/shop-refund-order.tx.ts` (new)                |
| "Wrapper around the Shippo SDK"                    | `lib/integrations/shippo/shipments.ts` (new)                       |

The examples show shape, not this app's names: always derive from doctrine.md and the app's modules.
