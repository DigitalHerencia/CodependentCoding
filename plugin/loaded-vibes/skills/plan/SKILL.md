# /plan: PRD to issues

Run inside an app generated by `hipster-stack new` (`hipster.json` at the repo root). The output is issue files plus execution state; write no application code.

## 0. Preconditions

```text
node "${CLAUDE_PLUGIN_ROOT}/scripts/governance-check.mjs" .
```

If it fails, the product is not defined yet: run `/idea` first. Then read:

- `context/specs/issues/README.md`: the issue format. It is the contract for every file you write.
- `context/docs/PRD.md` §3 goals, §4 non-goals, §5 capabilities, §6 entities, §7 flows.
- `context/docs/Architecture.md` §6 and `context/docs/AUTH.md` §12: domains, routes, permissions, resource policies.
- `.claude/execution/decisions.json`: accepted decisions shape issues; `proposed` ones become a `spike` issue or an open question, never silent scope.
- Existing files in `context/specs/issues/`: never renumber or overwrite one; continue after the highest id.

## 1. Decompose

Pick the id prefix once: two to four capital letters from the app name (GreenRoute → `GR`), recorded as a decision. Ids are `<PREFIX>-NNN` from `001`; the file is `<PREFIX>-NNN-<kebab-slug>.md`.

Walk PRD §5 in priority order and emit, per capability:

1. **Slice issue** for each new entity (`type: feature`, `size: m`): Scope starts with the exact `hipster-stack slice <entity> --module <id> --fields "<dsl>"` command from PRD §6, then the customizations the PRD asks for (list columns, detail fields, labels). Order slices so a `ref(Model)` target comes first and add it to `depends_on`.
2. **Rule issues** for what a slice cannot generate: AUTH §12 resource policies and new permissions (`lib/authz`, the module's grants), status transitions, named workflows (`lib/workflows/<module>Workflows.ts`), cross-entity flows from PRD §7. One rule per issue, `size: s` or `m`.
3. **Module issues** when a decision says to add a module: Scope is `hipster-stack add <module>` plus wiring.

Then, once per plan:

- An `<PREFIX>-NNN` `chore` for deployment from tech-requirements §5 (Vercel, Neon, Clerk env), depending on the p0 slices.
- A `test` issue per PRD §3 goal that a command can prove (e.g. a Playwright flow or a `validation.yaml` `app_checks` entry).

Rules:

- Sizes `xs` to `m`; anything bigger is split. Stay under 25 issues for v1; p2/p3 capabilities may stay as one `spike` each.
- `area` is the owning module id (or `base`), so ownership and file placement are clear. `milestone: "M1 · MVP"` for p0/p1, `"M2 · Next"` for the rest.
- Nothing from PRD §4 non-goals. A capability that needs a non-goal, a paid service or a doctrine change becomes a `spike` with the question in its Summary.
- Acceptance criteria are checks an agent can run: `pnpm validate`, `pnpm test`, `pnpm test:rls` for any new tenant table or policy, `pnpm build`, a named route rendering. No "works well".

## 2. Write each file

Front matter exactly as the README format (`id`, `title`, `type`, `area`, `milestone`, `priority`, `size`, `labels`, `depends_on`, `status: todo`), then the body sections in order: `# <ID> · <title>`, `## Summary`, `## Scope` (checklist), `## Acceptance criteria` (checklist), `## Validation` (fenced commands), `## Depends on` (ids or `none`), `## Definition of done` (as the README says). `labels` is `[type:<type>, area:<area>, priority:<p>, size:<s>]`.

## 3. Validate

```text
pnpm issues:sync
pnpm format
```

`pnpm issues:sync` without `--apply` is a dry run: it parses every file and exits 1 on a missing field, a bad enum, an id that does not match its file name, a missing section, a duplicate id or a `depends_on` with no file. Fix until it exits 0 and run `pnpm format:check`. Record both as EXECUTED evidence in `.claude/execution/progress.json`, and add each issue to `issues` with `status: todo`.

## 4. Execution state

- `decisions.json`: the id prefix, and any capability you split, deferred or turned into a spike.
- `handoff.json`: `status: ready`, `next_issue` = the first issue with no unmet `depends_on`, `queue` = the rest in dependency order, `notes` = one line on the plan.

## Record format

Write `.claude/execution/progress.json` only in the shape its `format` field spells out: statuses `todo`, `in-progress`, `in-review`, `done`, `blocked`; issue entries under `issues.<ID>`; one `evidence` entry per command, `{ "date", "state", "command", "result" }`, with `state` one of `EXECUTED`, `INSPECTED`, `NOT_RUN`, `BLOCKED`. Never add other top-level keys. Before handing back, run:

```text
node "${CLAUDE_PLUGIN_ROOT}/scripts/execution-check.mjs" .
```

Fix until it exits 0.

## 5. Hand back

Reply with a table (id, title, size, depends on), the next issue, and the open spikes. Then offer the GitHub sync:

```text
pnpm issues:sync --apply
```

It creates labels, milestones and issues in the repo's `origin`. That writes to GitHub: run it only when the owner says so, and record the result.
