# /idea: grill the owner, write the docs, compile the contracts

Run inside an app generated by `hipster-stack new` (a `hipster.json` sits at the repo root). If it is missing, stop: this skill only fills a generated app.

The output is the app's product definition, nothing else. Write no application code in this skill.

## 0. Read first (silently)

- `hipster.json` (installed modules, brand color), `hipster.modules.json` (what each module owns, presets).
- `context/docs/*.md` and `.claude/contracts/*.yaml`: note every `TODO`.
- `.claude/execution/decisions.json`: the next free `DEC-NNN`.
- `${CLAUDE_PLUGIN_ROOT}/references/doctrine.md`: the classifier and CC rules. Proposals must fit it.

If PRD.md has no `TODO` left, the product is already defined: ask whether to revise it before going further.

## 1. The grill (at most 12 questions)

Ask one question at a time, Mad-Libs style. Each question is a fill-in-the-blank sentence with your best guess already filled in from the earlier answers, so the owner can answer "yes", correct one blank, or say "skip". Never ask what an earlier answer already settled. A skipped question becomes a line under PRD §9 Open questions, never an invented answer.

`example.md` next to this file is a worked session (questions, answers, the commands handed back).

| #   | Fills                       | Ask (every `[blank]` carries your proposal)                                                                                      |
| --- | --------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 1   | PRD §1                      | "[who] loses [time, money, sanity] because [cause]; today they cope with [workaround]."                                          |
| 2   | PRD §2, AUTH §12            | "The people using it are [persona → owner, admin, member, viewer or portal client]. The one who pays is [persona]."              |
| 3   | PRD §6                      | "The app keeps track of [entity], [entity] and [entity]." (3 to 6 singular nouns)                                                |
| 4   | PRD §6                      | One question for all entities: "A [entity] has `[fields in the slice DSL]`. Right?"                                              |
| 5   | PRD §5, §3                  | "v1 ships these slices, in this order: 1. [capability] 2. [capability] 3. [capability]." (3 to 5, one entity each)               |
| 6   | PRD §4                      | "v1 will not [thing], [thing] or [thing]."                                                                                       |
| 7   | PRD §7                      | "The flow that makes or breaks it: [persona] opens [page], does [steps], and ends with [outcome]."                               |
| 8   | PRD §8, §3                  | "v1 works if [number with a unit and a time, e.g. a member logs a job in under 30 s]."                                           |
| 9   | modules                     | "Installed: [modules from hipster.json]. Keep them all and add [modules]?" plus each entity mapped to a module or new domain id. |
| 10  | AUTH §12                    | "Admins can [x] but not [y]; members can [x] but not [y]. Beyond roles: [rule, e.g. members edit only their own jobs]."          |
| 11  | Design §1, design.yaml      | "It should feel [tone] to [audience]. The brand color stays [color from hipster.json]."                                          |
| 12  | tech §4–5, application.yaml | "Beyond the stack: integrations [x], budgets [y], data rules [z]. You run commands in [PowerShell 7, zsh, ...]."                 |

Rules for the grill:

- Stop asking once all twelve are answered or skipped. Never exceed 12; fold clarifications into your next proposal instead of extra questions.
- Entities are singular camelCase (`job`, `lineItem`). Fields follow the slice DSL: `string`, `text`, `int`, `decimal`, `boolean`, `datetime`, `enum(a|b)`, `ref(Model)` with the field named `<relation>Id`; a trailing `?` means optional. A `ref` targets a tenant model or `User`.
- An entity an installed module already models (check `prisma/schema/<module>.prisma`) is not sliced again: it maps to that module.
- Anything that lands on a PRD non-goal, a paid service, or a doctrine change is noted, not designed: it goes to Open questions and a proposed decision.

## 2. Write the docs (owned sections only)

Replace each `TODO` with the answers. Keep every heading, table shape and HTML comment. Set the front matter `status: active` on PRD.md and tech-requirements.md and `updated:` to today.

| File                                | You may edit                                                     | Never touch                        |
| ----------------------------------- | ---------------------------------------------------------------- | ---------------------------------- |
| `context/docs/PRD.md`               | everything                                                       |                                    |
| `context/docs/tech-requirements.md` | §4 App-specific requirements, §5 Deployment                      | §1 to §3                           |
| `context/docs/Architecture.md`      | §1 System map, §6 App-specific architecture (one row per domain) | §2 to §5 (doctrine, lint-enforced) |
| `context/docs/AUTH.md`              | §12 App-specific access                                          | §1 to §11 (security doctrine)      |
| `context/docs/Design.md`            | §1 Visual principles, the app-specific paragraph only            | §2 to §6                           |

- Architecture §6 routes follow the slice convention: `/<plural>` and `/<plural>/[id]` inside `(tenant)`.
- AUTH §12 permissions follow §5.2 (`<module>.<resource>:<action>`); name them, do not implement them.
- A doctrine section that contradicts an answer stays as it is. Record the conflict as a proposed decision and tell the owner.

## 3. Compile the contracts

Edit only these keys; leave every other key byte-for-byte.

- `application.yaml`: `goals` (PRD §3, `{ id: G1, text, target }`), `non_goals` (PRD §4, strings), `environment.owner_shell`, `modules.domains` (Architecture §6: `{ id, entities: [...], routes: [...] }`), `updated`.
- `design.yaml`: `app` (`{ audience, tone, extras: [...] }` from Design §1), `updated`.
- `validation.yaml`: `app_checks` (tech §4 budgets as `{ id: AC1, text, run }` with a real command, or `[]` when there are none), `updated`.

Remove each `# TODO` comment you resolve. Quote strings that contain `:`, `#`, `|` or start with a symbol.

## 4. Record decisions

Append to `.claude/execution/decisions.json` (`decisions` array, next `DEC-NNN`, `status: accepted` unless marked proposed):

- One for the product definition: problem, personas, v1 slices, non-goals; refs `PRD.md`.
- One per module choice (kept, to add, or to drop) and per entity that maps onto an existing module instead of a new slice.
- One `status: proposed` entry per conflict or open question that needs the owner.

Update `updated` at the top of the file.

## 5. Check

```text
node "${CLAUDE_PLUGIN_ROOT}/scripts/governance-check.mjs" .
pnpm format
```

The check must exit 0: all three contracts parse and no `TODO` is left in the five docs or three contracts. Fix and rerun until it does; never report it passing without running it. Then run `pnpm format:check` and record both results as EXECUTED evidence in `.claude/execution/progress.json` (`evidence` array: date, state, command, result).

## Record format

Write `.claude/execution/progress.json` only in the shape its `format` field spells out: statuses `todo`, `in-progress`, `in-review`, `done`, `blocked`; issue entries under `issues.<ID>`; one `evidence` entry per command, `{ "date", "state", "command", "result" }`, with `state` one of `EXECUTED`, `INSPECTED`, `NOT_RUN`, `BLOCKED`. Never add other top-level keys. Before handing back, run:

```text
node "${CLAUDE_PLUGIN_ROOT}/scripts/execution-check.mjs" .
```

Fix until it exits 0.

## 6. Hand back

Reply with:

1. The v1 slices in order, and the `hipster-stack` commands that create them, one per new entity (use `--dry-run` first if the owner wants to preview):

   ```text
   hipster-stack add <module...>                      # only for modules to add
   hipster-stack slice <entity> --module <id> --fields "<dsl>" [--plural <word>] [--label "<Nav group>"] [--icon <name>]
   ```

   `--label`/`--icon` only on the first slice of a new module; icons: brain, briefcase, building, credit-card, folder-kanban, headphones, megaphone, users. Entities that an installed module already models get no command; say which module covers them. Order the commands so every `ref(Model)` target is sliced before the entity that points at it.

2. The decisions recorded (ids and one line each), the proposed ones first.
3. Open questions, if any.
4. Next step: `/plan` turns the PRD into issues.

Do not run the `slice` or `add` commands yourself in this skill; `/slice` does that per issue.
