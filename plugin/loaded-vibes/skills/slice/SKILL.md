# /slice: scaffold with the CLI, then fill the domain rules

Run inside an app generated by `hipster-stack new` (`hipster.json` at the root). The CLI writes the schema, RLS, selects, DTOs, fetchers, actions, Zod schemas, templates, features, routes, module definition and tests from the golden `projects` slice. You never hand-write those files; you change them only where a rule below says so.

## 1. Gather the slice

Take, in this order, from what exists rather than from the owner:

1. The issue (`context/specs/issues/<ID>-*.md`): its Scope has the exact `hipster-stack slice` command and the rules to implement.
2. PRD §6 (fields in the slice DSL), Architecture §6 (module id, routes), AUTH §12 (who may do what), `decisions.json`.
3. Only what is still missing: ask the owner one question with your proposal filled in.

The field DSL: `string`, `text`, `int`, `decimal`, `boolean`, `datetime`, `enum(a|b)`, `ref(Model)` with the field named `<relation>Id`; `?` makes a field optional. A `ref` target must already exist (a tenant model or `User`).

## 2. Scaffold

```text
hipster-stack slice <entity> --module <id> --fields "<dsl>" --dry-run
hipster-stack slice <entity> --module <id> --fields "<dsl>" [--plural <word>] [--label "<Nav group>"] [--icon <name>]
```

Read the dry-run file list first. `--label`/`--icon` only when the module is new. If the CLI refuses (existing model, file or export, unknown ref), stop and report its message; never work around it by writing the files yourself.

## 3. Fill the domain rules (and only those)

Classify every change with `/loaded-vibes:classify` rules (`${CLAUDE_PLUGIN_ROOT}/references/doctrine.md`) before editing. Never create a directory the classifier does not name.

| Rule from the issue or PRD                                    | Where it goes                                                               |
| ------------------------------------------------------------- | --------------------------------------------------------------------------- |
| Field constraints, cross-field rules ("skipped needs a note") | `schemas/<d>Schemas.ts`: `.refine` / `.superRefine` on the generated schema |
| Values the server derives ("stamp completedAt when done")     | the create/update action in `lib/actions/<d>Actions.ts`, after `parse`      |
| Who may do it beyond the role (owner of the row, crew lead)   | `lib/authz/policies.ts`, called from the action after `assertPermission`    |
| New permission (`<d>:<action>`)                               | the module's `lib/modules/<id>.module.ts` catalog and grants                |
| Multi-step logic reused by several actions                    | `lib/workflows/<d>Workflows.ts`                                             |
| Several writes that must succeed together                     | `lib/db/transactions/<d>-<verb>-<noun>.tx.ts`                               |
| List order, default filter, extra columns                     | the fetcher's query in `lib/fetchers/<d>Fetchers.ts`, then the template     |

Keep the generated shape: actions authenticate, authorize, parse, write inside the tenant transaction and return `ActionResult`; a rule violation the user can fix is a Zod error (`VALIDATION`), a forbidden actor is `FORBIDDEN`, a stale version stays `CONFLICT`.

Every rule gets a test next to the generated one in `tests/<module>/`: one case that passes and one that the rule rejects, with the expected `ActionResult` code.

## 4. Check

Run the app's profiles from `.claude/contracts/validation.yaml`:

```text
pnpm format
pnpm lint
pnpm typecheck
pnpm test
pnpm test:rls     # when DATABASE_URL_TEST is set; otherwise say it was not run
```

A lint finding prints a `CC-*` ID: fix the cause, never add `eslint-disable`. Rerun until all exit 0. Record each command and its result as EXECUTED evidence in `.claude/execution/progress.json` under the issue, and add a decision for any rule you had to interpret.

## Record format

Write `.claude/execution/progress.json` only in the shape its `format` field spells out: statuses `todo`, `in-progress`, `in-review`, `done`, `blocked`; issue entries under `issues.<ID>`; one `evidence` entry per command, `{ "date", "state", "command", "result" }`, with `state` one of `EXECUTED`, `INSPECTED`, `NOT_RUN`, `BLOCKED`. Never add other top-level keys. Before handing back, run:

```text
node "${CLAUDE_PLUGIN_ROOT}/scripts/execution-check.mjs" .
```

Fix until it exits 0.

## 5. Hand back

The files the CLI wrote (count), the files you changed for rules (each with one line why), the check results, and anything not run.
