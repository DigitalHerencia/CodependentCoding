# Chapter 01: Engineering Practice — Descriptive Model

**The Book of Knowledge™**

## Definition

- A descriptive engineering model explains how a person, team, organization, or engineering tradition actually understands and builds software. It is not automatically a governance system.
- Description and governance are different artifacts: description reconstructs practice; governance turns accepted practice into enforceable expectations.

## Canonical distinctions

- Keep **descriptive vs. normative** separate from **explanatory vs. operational**. A source can describe what happened, prescribe what should happen, explain why, or specify how to execute.
- Do not silently transform observed practice into doctrine or doctrine into evidence.

## Causal model

- Describe engineering as a causal chain: **context and constraints → values → conception of software → reasoning → decomposition → architecture → code organization → implementation → validation → delivery/operation → feedback and evolution**.
- A stack list, directory tree, or style guide is evidence about part of the practice; none is a complete engineering model.

## Evidence discipline

- Distinguish what the subject says, what formal materials prescribe, and what implementations demonstrate. Preserve disagreement instead of averaging contradictory sources together.
- Mark direct claims, observed behavior, inference, historical behavior, current behavior, unresolved ambiguity, and exceptions separately.

## Decision rule

- A descriptive claim becomes canonical doctrine only through an explicit normative decision. Evidence may motivate doctrine; it does not become doctrine by proximity.
