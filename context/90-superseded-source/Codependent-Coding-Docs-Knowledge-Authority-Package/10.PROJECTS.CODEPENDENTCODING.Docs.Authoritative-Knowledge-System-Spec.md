# 1. Purpose

The Codependent Coding™ Docs are the public, navigable documentation expression of the Codependent Coding™ knowledge system.

They are not a second architecture and not a rewritten collection of disconnected tutorials.

The Docs expose a connected body of:

```text
definitions
+ doctrine
+ architecture
+ patterns
+ contracts
+ lifecycles
+ security
+ governance
+ validation
+ provenance
+ reference evidence
```

The current source corpus already defines the knowledge system as a connected system of concepts, definitions, decisions, patterns, constraints, procedures, and evidence rather than a handbook-shaped rule list.

The website Docs preserve that principle.

# 2. Source Corpus

The current documentation corpus is organized into four authority-bearing areas:

```text
CodependentCoding/
├── docs/
├── patterns/
├── .agents/contracts/
└── provenance/
```

Each area has a different job.

## 2.1 `docs/` — explanatory canonical owners

`docs/` contains the human-readable explanatory canon.

It owns topics including:

- system identity and maps;
- knowledge-system definition;
- engineering doctrine;
- epistemology;
- formal knowledge modeling;
- terminology and nomenclature;
- architecture;
- technology map;
- layer contracts;
- system lifecycles;
- security;
- governance;
- specification;
- validation/conformance;
- agent execution;
- reference implementations.

These documents explain context, rationale, relationships, ownership, semantics, and limits.

## 2.2 `patterns/` — normative implementation grammar

`patterns/` contains the canonical reusable implementation patterns.

Patterns define how recurring architectural responsibilities are implemented.

The pattern catalog requires every canonical pattern to define twenty-one dimensions:

1. purpose/context;
2. responsibilities;
3. non-responsibilities;
4. inputs;
5. outputs;
6. dependencies;
7. callers;
8. callees;
9. invariants;
10. failure behavior;
11. security;
12. tenant isolation;
13. transaction behavior;
14. caching behavior;
15. validation;
16. testing;
17. naming;
18. placement;
19. lifecycle;
20. anti-patterns;
21. adjacent relationships.

Patterns are normative. They are not merely examples.

## 2.3 `.agents/contracts/` — deterministic machine-readable subsets

`.agents/contracts/` contains machine-comparable subsets of durable doctrine.

Current contracts:

```text
architecture.yaml
execution.yaml
ontology.yaml
product.yaml
validation.yaml
```

Contracts do not replace their explanatory Markdown owners.

They encode the stable subset suitable for:

- validation;
- agent constraints;
- architecture comparison;
- deterministic enforcement;
- automated conformance checks.

## 2.4 `provenance/` — source traceability and reconciliation

`provenance/` records:

- where doctrine came from;
- how sources were classified;
- how conflicts were resolved;
- what was adopted/refined/superseded/rejected;
- source-to-model traceability;
- source coverage;
- synthesis decisions.

Provenance exists so a reader can answer:

> Why does this rule exist, and what source/decision made it canonical?

It is not a runtime subsystem.

# 3. Knowledge Authority Model

The Docs follow this authority structure:

```text
Current controlling product direction / accepted decisions
        ↓
Canonical explanatory owner
        ↓
Canonical pattern / scoped specification
        ↓
Machine-readable deterministic contract
        ↓
Implementation + tests + validators
        ↓
Evidence
        ↓
Provenance / traceability
```

The exact ordering depends on the claim.

The governing epistemic rule is:

> **Truth is fact-specific.**

Examples:

```text
identity truth        → Clerk
application state     → PostgreSQL
provider payment fact → Stripe
product consequence   → application workflow/policy
architecture rule     → canonical docs/contracts
conformance evidence  → executed validation/review
```

---

# 4. Canonical Artifact States

Knowledge artifacts use the canonical states:

```text
canonical
supporting
implementation-evidence
project-specific
legacy
superseded
operational
```

Only canonical artifacts and accepted durable decisions create doctrine.

Supporting material explains doctrine.

Implementation evidence demonstrates or challenges it.

Operational state records current execution but cannot override canon.

Legacy and superseded material remain traceable but leave active authority paths.

# 5. Website Docs Are a Presentation of Canon

The website documentation layer SHOULD transform the repository corpus into a navigable documentation experience without changing ownership.

The website may:

- reorganize navigation;
- generate indexes;
- create landing pages;
- add cross-links;
- add diagrams;
- render contract tables;
- add examples;
- expose provenance links;
- provide code tabs;
- provide glossary/tooltips;
- add “related patterns” navigation.

The website MUST NOT silently:

- create competing definitions;
- flatten normative and supporting material into the same authority level;
- delete source provenance;
- present implementation evidence as canon;
- make a machine contract the sole explanation of a concept;
- copy stale terminology without reconciliation;
- generalize project-specific behavior into architecture.

# 7. Docs Content Classes

Every published Docs page SHOULD declare its content class.

## 7.1 Concept

Explains what something is.

Examples:

- Tenant;
- Feature;
- Workflow;
- Simple;
- Ontology;
- Virgule.

## 7.2 Architecture

Defines ownership, boundaries, dependency direction, topology, or invariants.

Examples:

- layer contracts;
- security architecture;
- route/feature orchestration.

## 7.3 Pattern

Defines reusable normative implementation grammar.

Examples:

- Fetcher;
- Server Action;
- Workflow;
- Transaction Helper.

## 7.4 Specification

Defines scoped required behavior and acceptance.

## 7.5 Contract

Encodes deterministic machine-comparable rules.

## 7.6 Lifecycle

Defines states, transitions, legality, concurrency, recovery, and evidence.

## 7.7 Governance

Defines how canonical truth and change are controlled.

## 7.8 Reference

Provides supporting or implementation evidence.

## 7.9 Provenance

Explains source lineage, reconciliation, and authority.

A page may link across classes but SHOULD have one primary owner class.

# 13. Security Documentation Rules

Security pages MUST preserve the current trust model:

- browser and external inputs begin untrusted;
- Clerk proves identity, not application authorization;
- PostgreSQL application state owns membership and product state;
- application policy decides authorization;
- RLS contains tenant data but does not replace authorization;
- provider objects remain bounded;
- network/provider work remains outside database transactions;
- webhooks are replayable/concurrent/out-of-order and require verified durable reconciliation;
- secrets never enter public docs or provenance.

Docs MUST distinguish explanatory examples from security requirements.

---

# 14. Validation and Evidence Semantics

The Docs MUST preserve the proof limitation model.

Evidence states:

```text
executed
skipped
blocked
inferred
```

A check may only be reported as passed when it actually ran for the relevant revision/environment.

The Docs SHOULD explicitly state what each validation mechanism proves and does not prove.

This prevents documentation from becoming confidence theater.

---

# 15. Governance and Change

A canonical docs change follows:

```text
identify canonical owner
    ↓
inspect affected docs / patterns / contracts / provenance
    ↓
resolve contradictions
    ↓
update one owner
    ↓
update dependent machine contracts
    ↓
update traceability / provenance when authority changed
    ↓
validate references / terminology / consistency
```

A new concept MUST NOT be defined independently in several pages.

One page owns the definition.

Other pages link to or use it.

---

# 16. Provenance Contract

When a reader asks why a rule exists:

```text
1. Read the owning canonical document.
2. Read the relevant synthesis decision.
3. Read the source provenance ledger.
4. Use specialized traceability for dense domains.
5. Consult implementation evidence only within its stated authority.
```

Provenance dispositions include:

```text
adopted
refined
superseded
rejected
consolidated
implementation evidence
```

Every material source conflict must have one selected outcome.

# 21. Docs Build Rules for Codex

When rebuilding the website Docs from this corpus, Codex MUST:

1. inspect the current canonical owner before rewriting a topic;
2. preserve source terminology unless a newer accepted authority supersedes it;
3. preserve normative/supporting/evidence/provenance distinctions;
4. never publish conflicting definitions as equally canonical;
5. link patterns to their owning architecture/lifecycle/security pages;
6. link machine contracts to explanatory owners;
7. retain provenance for material canonical decisions;
8. keep project-specific examples labeled as examples;
9. keep Vouch/project behavior from silently becoming generic doctrine;
10. distinguish current product naming from superseded source naming;
11. integrate Anthimeria, Simples, and Ontologies authorities into the current product taxonomy;
12. preserve proof limits and truthful validation semantics;
13. avoid new “service/manager” abstractions that contradict controlled terminology;
14. validate links, terminology, metadata, and authority labels;
15. keep the website Docs a presentation of the knowledge system rather than a parallel knowledge system.
