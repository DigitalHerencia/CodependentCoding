# The Codependent Coding™ Docs — Reconciliation and Migration Guide

This guide defines how the current CodependentCoding knowledge repository should be repurposed into the new website Docs without losing authority or carrying superseded product identities forward.

---

# 1. Preserve Before Rewriting

Preserve the technical and epistemic content of the current corpus unless a concrete newer authority supersedes it.

Do not treat a product rename as permission to rewrite:

- tenant security;
- RLS;
- transaction boundaries;
- fetcher/action behavior;
- evidence semantics;
- webhook recovery;
- pattern contracts;
- lifecycle rules;
- provenance.

---

# 2. Reconcile Product Identity First

The first migration pass should identify identity-bearing claims involving:

```text
Codependent Coding
Loaded Vibes
Hipster Stack
Maximal Template
Anthimeria
Simples
Ontologies
Virgule
Arrangement
```

Classify each occurrence:

```text
still canonical
needs rename
needs role correction
historical/provenance only
project-specific evidence
```

Do not global-search/replace blindly.

---

# 3. Integrate New Subject Authorities

Use the newest accepted subject authorities as canonical owners:

```text
Anthimeria Authority Package
Simples Authority Package
Ontologies Authority Package
```

Where these disagree with older explanatory pages, update the older page and provenance together.

---

# 4. Preserve the Four-Area Source Model

The refactor should retain the conceptual separation:

```text
docs/                 explanatory owners
patterns/             normative implementation grammar
.agents/contracts/    deterministic subset
provenance/           source lineage/reconciliation
```

The website may hide this filesystem distinction from casual users while still exposing authority relationships.

---

# 5. Page-by-Page Migration Procedure

For each existing page:

1. Identify its canonical topic.
2. Identify whether it still owns that topic.
3. Search newer decisions/authority packages for conflicts.
4. Classify each material statement by authority.
5. Update terminology/product roles where required.
6. Preserve technical doctrine not superseded.
7. Add links to patterns/contracts/provenance.
8. Add page metadata.
9. Validate internal references.
10. Record material reconciliation in provenance.

---

# 6. Pattern Migration Procedure

Pattern pages must retain all twenty-one contract dimensions.

When modernizing the page:

- preserve normative language;
- preserve explicit forbidden behavior;
- preserve transaction/cache/security/tenant sections;
- connect it to current architecture terms;
- connect it to machine contracts;
- preserve proof limitations;
- update examples only when necessary.

Do not compress canonical pattern pages into short blog-post summaries.

---

# 7. Contract Migration Procedure

Machine YAML remains source-controlled.

For website display:

```text
Markdown owner
    ↕
Machine contract
```

The website may pretty-print YAML or show a semantic summary.

Any change to a deterministic rule requires synchronized changes to the explanatory owner and contract.

---

# 8. Provenance Migration Procedure

Do not delete provenance after reconciliation.

Instead:

- mark superseded source roles;
- add new accepted decisions;
- extend conflict resolution when product definitions change;
- maintain source lineage;
- update coverage/traceability if ownership changes.

Historical evidence remains historical.

---

---

# 10. Current Definitions to Preserve Unless Separately Changed

The current corpus strongly establishes architectural distinctions that should not be lost during the website rewrite:

```text
authentication ≠ authorization
application authz ≠ RLS
provider state ≠ product state
route ≠ feature
feature ≠ component
fetcher ≠ arbitrary API helper
server action ≠ workflow
workflow ≠ transaction
transaction ≠ provider operation
DTO ≠ Prisma model
schema ≠ TypeScript type
evidence ≠ confidence
implementation ≠ canon
```

These distinctions are core knowledge assets.

---

# 11. Documentation QA

Before a migrated page becomes canonical website Docs, check:

- one canonical definition per consequential term;
- no unresolved competing product-role definitions;
- valid internal links;
- correct pattern links;
- correct machine-contract links;
- correct provenance links;
- authority/status metadata;
- no secret values;
- no project-specific behavior generalized silently;
- no unsupported claims of validation;
- no obsolete source treated as current doctrine.

---

# 12. Completion Standard

The migration is complete when:

```text
current accepted product identity
+
existing architectural knowledge
+
canonical patterns
+
machine contracts
+
provenance
=
one coherent website documentation system
```

A technically capable reader or constrained agent should be able to:

- locate the owner of a concept;
- understand what it means and excludes;
- follow its architecture relationships;
- find its implementation pattern;
- find deterministic constraints;
- find lifecycle/security consequences;
- find source provenance;
- implement without inventing a competing architecture.
