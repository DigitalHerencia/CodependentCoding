# The Loaded Vibes™ Codex Plugin

## Authoritative Arrangement Execution Specification

# 1. Governing definition

> **Loaded Vibes™ is the Codex-oriented architecture-enforcement and software-operations layer purpose-built for The Arrangement™ Generated Artifact. It turns the Codependent Coding™ WebApp Architecture into executable agent guidance, narrow reusable skills, deterministic validators, proportional verification, and repository-development assets.**

Loaded Vibes operates **after generation**.

It does not own Virgule normalization, Maximal Template pruning, or Arrangement materialization. Those belong to The Hipster Stack™ generation system.

# 2. System position

```text
Codependent Coding™ WebApp Architecture
               ↓ governs
The Hipster Stack™ + Maximal Template™
               ↓ generate
       The Arrangement™
               ↑ operate on
        Loaded Vibes™
```

# 3. Primary purpose

Loaded Vibes exists so a coding agent working inside an Arrangement does not need to rediscover:

- where a new responsibility belongs;
- what a route may own;
- what a Feature may orchestrate;
- what PureUI Blocks may import;
- where persisted reads and CRUD writes live;
- how Workflows differ from Actions and Transactions;
- how auth differs from authz;
- where provider mechanics and webhook HTTP boundaries live;
- how tenant/RLS/security boundaries are preserved;
- which checks prove completion;
- how Git/GitHub delivery is evidenced.

# 4. Universal workflow

```text
inspect actual state
    ↓
classify owning responsibility
    ↓
plan smallest complete change
    ↓
implement in the owning layer
    ↓
review architecture/security drift
    ↓
run proportional verification
    ↓
report executed evidence
    ↓
Git/GitHub delivery when requested
```

This replaces the historical assumption that every task must traverse a fixed sequence of eighteen ceremonial DevCycles.

# 5. Canonical content families

## 5.1 Skills

The plugin uses a small, discriminating skill set:

```text
loaded-vibes-inspect
loaded-vibes-classify
loaded-vibes-implement
loaded-vibes-review
loaded-vibes-verify
loaded-vibes-deliver
```

Skills are the primary reusable workflow unit.

They use progressive disclosure: short trigger metadata, focused SKILL.md guidance, and supporting references/scripts only when needed.

## 5.2 Project agents

Three responsibility-oriented agent roles are provided as project assets:

```text
arrangement-engineer
arrangement-reviewer
arrangement-verifier
```

They are deliberately not personality simulators.

Their job is to give spawned Codex sessions a narrow execution/review/verification role when the local Codex runtime supports project-scoped custom agents.

## 5.3 Instructions

Instruction slices preserve stable invariants:

```text
architecture
security
validation/evidence
delivery
```

They are not a second architecture knowledge system.

## 5.4 Prompts

Prompts are thin execution adapters that invoke skills. They must not contain a duplicated civilization-sized orchestration framework.

## 5.5 Deterministic scripts

Scripts perform repeatable work that should not be re-reasoned from scratch:

```text
inspect Arrangement structure
validate mechanical architecture rules
smoke-test Arrangement shape
validate plugin package structure
install project assets conservatively
```

## 5.6 Developer-environment assets

The package provides conservative templates for:

- AGENTS.md;
- `.codex/agents/*.toml`;
- Codex config example;
- ESLint architecture fragment;
- Prettier baseline;
- `.editorconfig`;
- `.gitattributes`;
- `.gitignore` fragment;
- commit instructions;
- PR instructions.

These assets are merged/adopted deliberately. The plugin must not overwrite unrelated repository configuration silently.

# 6. Architecture enforcement scope

Mechanical validation may reliably check stable syntax/import/placement evidence such as:

- PureUI Blocks importing server/provider responsibilities;
- normal Features importing raw UI primitives without the React Hook Form exception;
- fetchers containing obvious mutation calls;
- transaction helpers containing obvious provider/network dependencies;
- Actions/Workflows importing provider SDKs directly;
- page routes importing database/application implementation directly;
- generator/research debris appearing inside an Arrangement.

Mechanical validators must **not** claim to prove semantic facts they cannot establish, such as complete authorization correctness, business invariant correctness, perfect RLS coverage, or webhook idempotency from import shape alone.

# 7. Security operating model

Loaded Vibes preserves, rather than invents, the Arrangement security model.

It treats the following as high-signal review boundaries:

```text
identity → authentication
access decision → authorization
resource/tenant predicate → persisted operation
PostgreSQL RLS → containment
authenticated provider request → webhook boundary
provider truth → integration/reconciliation
atomic DB invariant → transaction
```

It must not weaken those boundaries to make implementation easier.

# 8. Proportional process

The plugin intentionally rejects the old “simulate an entire software organization on every edit” behavior.

For a small UI change, do not automatically create:

- ADRs;
- roadmap updates;
- security reports;
- observability changes;
- CI changes;
- changelog entries;
- Issue trees.

For a consequential tenancy, migration, webhook, provider, or authorization change, deeper review and evidence may be required.

Process scales with consequence and blast radius.

# 9. Repository authority

When operating inside an Arrangement, precedence is:

1. current explicit user request;
2. repository-local AGENTS/instructions/contracts;
3. current repository implementation and accepted exceptions;
4. Loaded Vibes canonical architecture derivatives;
5. historical/reference material.

Loaded Vibes does not silently replace repository-local truth.

# 10. Historical material disposition

The supplied historical Loaded Vibes archive contains useful ancestors:

```text
context acquisition
phase instructions/prompts
tool-boundary thinking
repository inspection scripts
validation hooks
audit integrity
security scanning
GitHub delivery skills
```

The following are superseded and must not be revived as product architecture:

- GenAIScript orchestration;
- fixed 18-DevCycle execution requirement;
- `.loaded-vibes` runtime state as a mandatory framework;
- broad automatic TODO/changelog/ceremony updates;
- old `src/**` ownership assumptions;
- declared toolset permissions presented as runtime enforcement;
- old route/Server Action placement rules;
- generic Awesome Copilot corpus shipping inside the plugin.

# 11. Current Codex packaging boundary

The Codex-native unit of reusable procedural knowledge is a skill folder containing `SKILL.md` plus optional scripts/references/assets and `agents/openai.yaml` UI metadata.

Current custom subagent roles are project/user configuration. Therefore this package supplies agent TOML files as project assets rather than pretending plugin installation necessarily registers them automatically.

The portable `plugin.json` is package metadata derived from the supplied plugin-reference convention. Publication to a specific Plugin Directory ingestion pipeline requires validation against that pipeline at publication time.

# 12. Completion/evidence rule

Loaded Vibes distinguishes:

```text
expected     ≠ passed
configured   ≠ working
generated    ≠ validated
provider-ready ≠ source-present
deployed     ≠ smoke-verified
```

A completion claim requires executed evidence or an explicit statement of what remains unverified.

# 13. Anti-goals

Loaded Vibes must not:

- become the generator;
- become a generic stack-agnostic prompt bundle;
- redesign healthy architecture on every task;
- create a second resolver/configuration model;
- add speculative abstractions;
- create ceremony unrelated to the requested outcome;
- cosplay runtime permission enforcement with declarative files;
- copy a giant third-party reference corpus into the package;
- report unrun checks as passed;
- perform consequential external actions without authorization.

# 14. Canonical sentence

> **Loaded Vibes™ is the post-generation Codex execution environment for The Arrangement™: a small set of architecture-aware skills, responsibility-oriented project agents, invariant instructions, thin prompts, deterministic validators, smoke tests, and developer-environment assets that help Codex inspect reality, classify ownership, implement bounded changes, preserve security and architecture boundaries, verify proportional evidence, and deliver repository changes without architecture drift.**
