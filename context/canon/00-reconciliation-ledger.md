# Doctrine Reconciliation Ledger

This is the decision record behind the Canon. Every rule in `doctrine/` that differs from something previously written, locked or built is listed with the sources that disagree, the decision, and the reason. Every row is decided; nothing here waits on anyone. Where a tracker lock is overturned, it is because code, a vendor document, or a correctness argument contradicts it, and that argument is written out so it can be read line by line.

### 3.1 Architecture and call graph

| #   | Topic                                              | Sources in conflict                                                                                                                                                                                                                                                                                   | Verdict                                                                                                                      | Reason                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| --- | -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A-1 | Do workflows import actions?                       | T L4: "Workflows call fetchers, actions, and other lib helpers." E1 BusinessLogic Blocks: workflows compose Actions. L Ch.14: same. R CANONICAL-RECONSTRUCTION: Action → Workflow. C: both directions exist (`crmWorkflows.ts` imports `crmActions`; `uploadsActions.ts` imports `uploadsWorkflows`). | **AMEND.** Workflows never import a `"use server"` module. Actions may call workflows. Features call workflows and fetchers. | (1) **Atomicity.** Every action opens its own `withTenantTransaction`. A workflow that calls two actions commits twice; a failure between them leaves half a business operation. `qualifyLeadWorkflow` reads the contact in one transaction and writes it in a second, protected only by `expectedUpdatedAt`. (2) **Public surface.** Every exported `"use server"` function is a POST endpoint (Next.js data-security guide). An internal composition step should not also be an internet endpoint. (3) **Cycles.** Action ↔ workflow imports in both directions make the module graph cyclic. (4) **Envelopes.** Actions return `ActionResult` and call `revalidatePath`; a workflow composing them unwraps envelopes and fires cache invalidation mid-operation. Your symmetry survives: helpers → workflow → feature on the read side, form → action → workflow on the write side. |
| A-2 | Action order: authorize before or after Zod parse? | T L2/L4: authenticate, authorize, Zod parse, write. C: authenticate, open transaction, authorize, parse. Parsing is CPU-only, capped at the 1 MB action body limit, and the schemas are already public (forms ship them to the browser), so parsing first leaks nothing and spends nothing. The tracker's goal ("reject before spending work on unauthenticated callers") is fully met by authenticating and rate-limiting first. The template's order wastes a pooled connection on invalid input.                                                                                                                                                                                                                                                                                                                    |
