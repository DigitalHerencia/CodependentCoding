# Canonical System Manifest

## 1. System chain

```text
TypeScripture™ Canonical Doctrine
  ↓ governs meaning + implementation doctrine
Codependent Coding™ Web App Architecture
  ↓ realized by
The Hipster Stack™ Technology Stack
  + The Maximal Template™ Domain Library
  ↓ normalized defaults
The Ontology™ (9 starter Application Definitions)
  ↓ selected/configured through
The Anthimeria™ Workbench + CLI/config adapters
  ↓ shared resolver
The Virgule™ Application Definition (dependency-closed)
  ↓ generation plan + materializer
The Arrangement™ Generated Artifact
  ↓ post-generation development/operations
The Loaded Vibes™ Codex Plugin
```

Presentation is supplied by **Visual Vibes™** and exposed through **PureUI Blocks™**. Application behavior is exposed through **BusinessLogic Blocks™ / Workflows**. Together those two block families constitute **Simples™**.

## 2. Core equations

```text
Simples™

```

```text

```

## 3. Behavioral boundary

The canonical application grammar remains:

```text
Routes adapt.
Features orchestrate.
Pure presentation renders.
Fetchers read.
Actions adapt mutations.
Workflows coordinate use cases.
Schemas validate.
Authorization decides.
Transactions preserve invariants.
Integration adapters own provider mechanics.
Webhooks reconcile external truth.
```

## 4. Anthimeria configuration boundary

Anthimeria is **stateless** and MUST delegate to the same schema/resolver used by CLI/config materialization.

User-configurable intent is primarily presentation-oriented:

- select one of nine normalized Ontologies;
- product identity/copy where supported;
- page topology and feature-slot presentation where supported;
- compatible PureUI Block selections/variations;
- compatible UI primitive variants where the block contract permits it;
- semantic design tokens and presentation settings;
- export/copy/share of the portable definition.

Anthimeria MUST NOT become an arbitrary toggle board for:

- BusinessLogic workflow membership;
- workflow constituent files;
- actions/fetchers/auth/authz/transactions/selects/DTOs;
- provider mechanics;
- persistence or authorization invariants;
- dependency closure.

The selected Ontology determines normalized behavior. The resolver establishes closure. Virgule records resolved authority.

## 5. Simples boundary

A top-level Simple is exactly one of:

1. **PureUI Block™** — reusable presentation constitution; or
2. **BusinessLogic Block™** — normalized domain Workflow constitution.

UI primitives, actions, fetchers, schemas, types, integrations, routes, features, templates, and helpers are constituents/relationships, not additional Simple families.

## 6. Maximal Template boundary

There is one runnable superset application containing all supported implementation source. The generator retains, removes, or transforms owned artifacts based on a dependency-closed Virgule. Do not maintain nine independent template applications.

## 7. Arrangement boundary

An Arrangement is standalone source. It may preserve `hipsterstack.json` and provenance metadata, but it does not require Anthimeria, the Hipster Stack runtime, the generator workspace, or the Codependent Coding website at runtime.

## 8. Loaded Vibes boundary

Loaded Vibes operates **after generation** on an Arrangement. It does not own Virgule normalization, Maximal Template pruning, or Arrangement materialization.
