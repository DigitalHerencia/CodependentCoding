# Reference-Implementation Relationship

| Class | Meaning | Authority |
|---|---|---|
| Canonical doctrine | Why and what MUST remain true | highest reusable source-derived authority |
| Canonical architecture | Stable form, boundaries, and ownership | governs implementations |
| Reference implementation | Concrete evidence demonstrating some architecture | evidence, not automatic doctrine |
| Reusable template | Frozen instantiation distributed as a baseline | must conform to architecture |
| Generator output | Configured template instance | validated result, not source authority |
| Project implementation | Product-specific specialization | local authority only within approved specs |
| Legacy behavior | Retained historical behavior or documentation | non-authoritative unless re-adopted |
| Experimental behavior | Time-bounded investigation | no canonical authority |

Vouch is the strongest complete application evidence in the source set for server-first boundaries, lifecycle discipline, Stripe/Clerk reconciliation, and validation. Its business ontology, route allowlist, lifecycle states, confirmation protocol, copy, and product exclusions are Vouch-specific and MUST NOT become generic doctrine.

Vibes demonstrates the current golden-template direction and validation assets. Loaded Vibes™ is the architecture/generator concept that deterministically produces a conforming baseline; it is not identical to one Vibes commit. Control Plus supplies additional boundary and agent-workflow evidence where compatible.

The historical CodependentCoding transcript application is a prior product sharing a name. It does not define the current Codependent Coding™ Knowledge System. Its existence is recorded as superseded implementation evidence; current identity comes from this repository and controlling decisions.

Promotion rule: behavior may become canonical only when reusable, compatible with doctrine/security, intentionally accepted, given one owner, reflected in contracts/tests, and recorded in the decision register.
