# Spec 06 — Turn the Application Shell into the Maximal Template Explorer

**Priority:** P6  
**Depends on:** Spec 05

## Goal

Make the breadth of The Maximal Template™ immediately discoverable from the public demo.

The application shell should function as an application explorer, not a sparse SaaS sidebar.

## Problem

The current navigation exposes only a small subset of the maximal application, making major recipe domains effectively invisible.

The template already has seeded/publicly visible data that can make the demo compelling, but the information architecture does not surface it.

## Required navigation model

Expose clear access to:

- Home / Public;
- Dashboard;
- CRM;
- Projects;
- Support;
- Marketing;
- Invoicing;
- Social;
- AI;
- Portal;
- Admin;
- User / Settings;
- Auth / Onboarding examples;
- Integrations;
- Components / Blocks;
- Architecture / Security context where useful.

Do not make every leaf route a top-level item.

Use grouping/subnavigation where that improves scanability.

## Public demo behavior

Navigation must work for signed-out visitors.

Do not hide major recipe areas merely because real mutations require authentication.

Auth state controls actions, not the visitor's ability to inspect the template.

## Demo context labels

Where useful, application surfaces may show compact architecture/status badges such as:

```text
SEED DATA
DATABASE READ
RLS SCOPED
RBAC
ABAC
CLERK
PRISMA
NEON
STRIPE
WEBHOOK
SERVER COMPONENT
CLIENT FEATURE
REACT HOOK FORM
```

These badges should explain the surface being viewed.

They must not overwhelm the UI or turn the application into a documentation dashboard.

## Integrations surface

Provide a clear integrations/status surface that can show:

- configured;
- demo-only;
- missing secret;
- not provisioned;
- live/sandbox where safe and meaningful.

Do not expose secret values.

## Components / Blocks surface

If the repository already has or needs a block/component catalog, expose it as part of the explorer so the public demo can demonstrate reusable presentation material.

The catalog must not pull logic back into blocks.

## Architecture/security surface

Use concise explanatory panels where valuable.

The goal is to help a visitor understand the architecture in the application, not reproduce the full context docs.

## Shell constraints

`components/shells` and `components/nav` remain presentation/structure.

They do not own:

- persisted data access;
- authorization policy;
- provider SDK calls;
- business workflows.

Any dynamic status data needed by the shell must be supplied by an appropriate feature/fetcher boundary.

## Acceptance criteria

- [ ] Every major recipe domain is discoverable from the public shell.
- [ ] Signed-out visitors can navigate the demo.
- [ ] Sign-in remains available but is not the main navigation gate.
- [ ] Navigation does not collapse the `marketing` business domain into public pages.
- [ ] Admin points to real `/admin/*` routes.
- [ ] Architecture/status badges are contextual and restrained.
- [ ] Integration status is visible without exposing secrets.
- [ ] Components/blocks can be inspected through the demo when the catalog exists.
- [ ] Nav/shell components remain presentation-only.
- [ ] The application feels like a coherent maximal system rather than disconnected recipe demos.
