# Spec 05 — Normalize `lib/`, `types/`, `schemas/`, and the Webhook Write Boundary

**Priority:** P5  
**Depends on:** Spec 04

## Goal

Normalize application-library placement and naming after the CRM golden slice has established the reference grammar.

Do not explode the repository into one-function-per-file hierarchy.

## 1. Actions

Normalize domain files toward:

```text
lib/actions/
├── crmActions.ts
├── projectsActions.ts
├── supportActions.ts
├── marketingActions.ts
├── invoicingActions.ts
├── socialActions.ts
├── aiActions.ts
├── portalActions.ts
├── adminActions.ts
├── userActions.ts
└── commonActions.ts   # only if genuinely needed
```

Do not create files merely for symmetry.

Every exported action must be audited:

- ordinary CRUD write → stays in actions;
- persisted read → move to fetchers;
- provider operation → move to integration/workflow as appropriate;
- non-CRUD business logic → move to workflow;
- generic helper → classify precisely.

Audit vague `foundation` naming and reclassify into `common`, `user`, `admin`, or another actual domain.

## 2. Fetchers

Normalize domain files toward:

```text
lib/fetchers/
├── crmFetchers.ts
├── projectsFetchers.ts
├── supportFetchers.ts
├── marketingFetchers.ts
├── invoicingFetchers.ts
├── socialFetchers.ts
├── aiFetchers.ts
├── portalFetchers.ts
├── adminFetchers.ts
├── userFetchers.ts
└── commonFetchers.ts   # only if genuinely needed
```

Every persisted application read must be represented here.

Fetchers remain read-only.

## 3. Database root

Normalize `lib/db` around clear database responsibilities.

Target conceptual structure:

```text
lib/db/
├── client.ts
├── selects/
├── dto/
└── transactions/
```

Audit existing root files such as:

```text
neon.ts
prisma.ts
provider.ts
tenant.ts
```

Keep a separate file only when it owns a real distinct database responsibility.

Do not hide Prisma behind unnecessary wrappers.

## 4. Loose `lib` root files

Classify files currently squatting at `lib/` root, including:

```text
chart-export.ts
math-curves.ts
motion-core.ts
```

Possible destinations are `lib/utils`, a domain workflow, or another precise existing category.

Do not keep uncategorized root helpers.

## 5. Types

Replace generic catch-all type files where domain ownership is clearer.

Direction:

```text
types/crmTypes.ts
types/projectsTypes.ts
types/supportTypes.ts
types/marketingTypes.ts
types/invoicingTypes.ts
types/socialTypes.ts
types/aiTypes.ts
types/portalTypes.ts
types/adminTypes.ts
types/userTypes.ts
types/commonTypes.ts
```

Only create a file when there is an actual shared contract.

## 6. Schemas

Replace giant mutation-schema buckets with domain schemas:

```text
schemas/crmSchemas.ts
schemas/projectsSchemas.ts
schemas/supportSchemas.ts
schemas/marketingSchemas.ts
schemas/invoicingSchemas.ts
schemas/socialSchemas.ts
schemas/aiSchemas.ts
schemas/portalSchemas.ts
schemas/adminSchemas.ts
schemas/userSchemas.ts
schemas/commonSchemas.ts
```

Again: no symmetry-only files.

## 7. Workflows

Keep:

```text
lib/workflows/{domain}/
```

shallow.

Move only remaining business logic there.

Do not create service/repository/use-case hierarchies.

## 8. Clerk webhook persistence boundary

Canonical HTTP boundary remains:

```text
app/api/clerk/webhooks/route.ts
```

The route may use `lib/auth` helpers for Clerk-specific interpretation/identity behavior.

The current `lib/auth/syncWebhook.ts` pattern must be audited so it does not directly become an unclassified database service.

Move reusable atomic persistence to transaction helpers under:

```text
lib/db/transactions/
```

The webhook route remains responsible for the HTTP lifecycle and idempotency sequence.

Webhook-driven writes are a special system boundary and do not need to masquerade as user CRUD actions.

## 9. Environment consistency

Fix `.env.example` and code mismatches.

At minimum align the Clerk webhook secret name.

Audit provider environment keys before Spec 07.

## 10. Acceptance criteria

- [ ] Domain action/fetcher filenames use the canonical naming scheme.
- [ ] Every action export is genuinely an ordinary CRUD write.
- [ ] Every fetcher export is read-only.
- [ ] All persisted application reads are routed through fetchers.
- [ ] `foundation` naming is removed or justified.
- [ ] `lib/db` root responsibilities are simplified and clear.
- [ ] Loose root helpers are classified.
- [ ] `types/` is domain-organized where useful.
- [ ] `schemas/` is domain-organized where useful.
- [ ] No symmetry-only schema/type files are created.
- [ ] Workflow hierarchy remains shallow.
- [ ] Clerk webhook HTTP lifecycle remains in `app/api/clerk/webhooks/route.ts`.
- [ ] Reusable webhook persistence lives in the database transaction boundary.
- [ ] Auth helpers do not secretly become generic database services.
- [ ] `.env.example` matches actual canonical environment key names.
- [ ] Relevant format/lint/type/Prisma/build checks pass.
