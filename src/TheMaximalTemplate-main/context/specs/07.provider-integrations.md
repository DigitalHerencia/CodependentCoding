# Spec 07 — Finish the External-Provider Story

**Priority:** P7  
**Depends on:** Spec 06

## Goal

Finish provider configuration and demonstration only after core architecture, routes, design, blocks, vertical-slice grammar, and library boundaries are stable.

## Existing provider code

The repository already contains dependencies and integration directories for:

- Stripe;
- Vercel Blob;
- Cloudinary;
- SendGrid;
- Hugging Face.

Do not treat those directories as proof that the provider is fully configured or demonstrated.

## Implementation order

Use this order unless current repository evidence establishes a blocker:

1. Stripe;
2. Vercel Blob / Cloudinary;
3. SendGrid;
4. Hugging Face.

Do not add extra providers simply because an old stub exists.

## Global integration rules

Provider-specific code belongs under:

```text
lib/integrations/{provider}/
```

Exceptions remain:

```text
Clerk  → lib/auth
Neon   → lib/db
Prisma → lib/db runtime + root prisma lifecycle
```

Provider SDKs do not leak into blocks, normal features, fetchers, or generic utilities.

## Missing-configuration behavior

Optional provider secrets must not make unrelated public routes crash.

A provider demo surface should report a clear state such as:

```text
CONFIGURED
DEMO MODE
MISSING SECRET
NOT PROVISIONED
```

Do not silently fake a live provider success.

Do not require the public visitor to supply credentials.

## `.env.example`

Document every provider key actually used by code.

Do not include real secrets.

Keep names aligned exactly with implementation.

## Stripe

Audit and complete the existing Stripe integration family, including the current equivalents of:

- client;
- checkout;
- customer portal;
- subscriptions;
- webhook verification/normalization.

Required webhook boundary:

```text
app/api/stripe/webhooks/route.ts
```

Webhook verification occurs before payload trust.

Provider state remains provider-owned.

Application consequences are persisted as bounded local state.

Public demo actions may remain disabled/demo-labeled when Stripe is not configured.

## Vercel Blob

Use for file/object storage where the recipe actually calls for it.

Keep storage behavior in `lib/integrations/vercel-blob`.

Persist only application metadata/ownership necessary for the local domain model.

## Cloudinary

Use for image/media transformation and upload behavior where useful.

Do not duplicate Blob and Cloudinary responsibilities without a deliberate reason.

The demo should make the selected purpose of each provider understandable.

## SendGrid

Use for email delivery/event behavior where the supported recipe requires it.

If webhook/event intake is implemented, use:

```text
app/api/sendgrid/webhooks/route.ts
```

Verify provider authenticity before trusting events.

## Hugging Face

Use for AI inference/provider behavior under:

```text
lib/integrations/hugging-face/
```

Model/provider mechanics stay in the adapter.

Application usage, credits, rate limits, or product rules remain in the AI domain workflow/authz layers.

## Public demo surface

Expose meaningful provider status and safe demonstrations without:

- leaking secrets;
- executing unexpected live mutations;
- blocking unrelated routes;
- pretending an unconfigured provider is live.

## Provider provisioning

Live account provisioning, webhook endpoint registration, secret creation/rotation, and other external mutations require explicit user authorization.

The implementation can prepare the code and exact configuration requirements without performing the live operation.

## Acceptance criteria

- [ ] `.env.example` documents the actual optional provider keys used by code.
- [ ] Stripe code is internally coherent and has a real Route Handler boundary for webhook HTTP.
- [ ] Blob and Cloudinary have distinct, understandable responsibilities.
- [ ] SendGrid integration is isolated and webhook verification exists if event intake is used.
- [ ] Hugging Face provider mechanics remain inside its integration directory.
- [ ] Provider SDKs do not leak into inappropriate layers.
- [ ] Missing optional provider secrets do not crash unrelated public demo routes.
- [ ] Demo/provider status is explicit rather than silently faked.
- [ ] Live provider mutation/provisioning is not performed without explicit approval.
- [ ] Public browseability remains intact.
- [ ] Relevant targeted validation and production build pass when executed.
