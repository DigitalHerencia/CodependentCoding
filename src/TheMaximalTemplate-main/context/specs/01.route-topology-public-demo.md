# Spec 01 — Repair Route Topology and Public-Demo Information Architecture

**Priority:** P1  
**Depends on:** Spec 00

## Problem

The current route topology does not express the intended application domains.

Known defect:

```text
app/(admin)/users/page.tsx
```

produces `/users`, not `/admin/users`, because `(admin)` is a route group.

Production evidence has shown:

```text
/admin/users → 404
/users       → admin users surface
```

The repository also uses `(marketing)` for static public pages and wraps those routes with `features/marketing/*`, which conflicts with the canonical distinction between public content and the marketing-automation business domain.

## Required target topology

```text
app/
├── (public)/
│   ├── page.tsx
│   ├── features/page.tsx
│   ├── pricing/page.tsx
│   ├── faq/page.tsx
│   ├── contact/page.tsx
│   ├── terms/page.tsx
│   └── privacy/page.tsx
├── (auth)/
│   ├── sign-in/...
│   └── sign-up/...
├── onboarding/ or the approved public-demo equivalent
├── (tenant)/
│   ├── dashboard/
│   ├── crm/
│   ├── projects/
│   ├── support/
│   ├── marketing/
│   ├── invoicing/
│   ├── social/
│   ├── ai/
│   ├── portal/
│   ├── admin/
│   ├── user/
│   └── settings/
└── api/
    ├── clerk/...
    ├── stripe/...
    └── sendgrid/...
```

## Public route rules

For static public pages:

- compose blocks directly in `page.tsx`;
- do not create `LandingFeature`, `PricingFeature`, `ContactFeature`, etc. without actual orchestration;
- do not create public-page fetchers/actions/schemas/types unless the page genuinely needs them;
- public navigation should lead into the application demo, not only into sign-up.

## Required public routes

At minimum normalize:

- `/`;
- `/features`;
- `/pricing`;
- `/faq`;
- `/contact`;
- `/terms`;
- `/privacy` if already represented or required by current content.

Do not create legal claims that are not already approved. Placeholder legal surfaces may remain clearly generic template content.

## Admin topology

Move or recreate admin route surfaces under a real `admin` URL segment.

Required canonical paths:

```text
/admin/users
/admin/records
/admin/audit
```

The shared tenant shell may still come from `(tenant)`.

Do not create a second admin shell/data architecture unless the real UX requires one.

## CRM topology requirement

CRM contacts must follow the canonical resource grammar:

```text
/crm/contacts
/crm/contacts/new
/crm/contacts/[contactId]
/crm/contacts/[contactId]/edit
```

Do not implement the full CRM vertical slice in this spec; establish the routes and thin entrypoints needed for Spec 04.

## Route/page responsibility

Pages own only:

- params/search adaptation;
- Suspense placement;
- feature/form entrypoint;
- metadata;
- loading/error/not-found/redirect framework behavior.

No Prisma/provider SDK/business workflow logic in pages.

## Public demo visibility

The application must remain browseable signed out.

Navigation and routing must not globally redirect visitors to auth/onboarding merely to inspect recipe surfaces.

Sign-in/sign-up remain available as explicit example routes.

## Deletions / migrations

Remove or supersede:

- `app/(marketing)` for static public content;
- root/static public routes that conflict with the new `(public)` organization;
- `(admin)` route-group usage that causes incorrect public URLs;
- static `features/marketing/*` wrappers that only render public content.

Preserve actual marketing-automation features under `features/marketing/`.

## Acceptance criteria

- [ ] `/admin/users`, `/admin/records`, and `/admin/audit` resolve at those URLs.
- [ ] Old accidental `/users`, `/records`, and `/audit` admin URLs no longer exist unless deliberately redirected.
- [ ] Static public content lives under `(public)`.
- [ ] Public static pages compose blocks directly when no orchestration exists.
- [ ] `features/marketing/` contains only real marketing-domain orchestration.
- [ ] `/crm/contacts`, `/new`, `/[contactId]`, `/[contactId]/edit` route entrypoints exist.
- [ ] Public visitors can browse major demo routes signed out.
- [ ] Protected mutations are not made anonymous merely to satisfy demo browseability.
- [ ] Thin-page architecture is preserved.
- [ ] Relevant route/build validation passes.
