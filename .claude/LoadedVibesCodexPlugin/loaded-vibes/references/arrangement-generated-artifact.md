# The Arrangement™ Generated Artifact

## Authoritative Contract

# 1. Definition

> **The Arrangement™ is the generated standalone white-label application produced by resolving a valid dependency-closed Virgule™ against The Maximal Template™ through The Hipster Stack™ generation system.**

Equation:

```text
dependency-closed Virgule
+
The Hipster Stack generator
+
The Maximal Template
=
The Arrangement
```

---

# 2. Required Properties

An Arrangement should be:

- standalone;
- white-label;
- runnable;
- normal source code;
- understandable without generator internals;
- architecture-conformant;
- dependency-complete;
- limited to supported capabilities;
- free of intentionally removed maximal-only surfaces;
- equipped with required local configuration/examples without secrets;
- independently source-control-owned after generation.

---

# 3. What It Contains

An Arrangement may contain:

```text
app code
features
PureUI Blocks
UI primitives
content
BusinessLogic Workflows
server operations/helpers
schemas/types
Prisma schema/migrations
tests
application docs
app-local governance/contracts
.env.example
supported CI/deployment config
portable generation provenance
```

The exact inventory is resolved from Virgule.

---

# 4. What It Does Not Require

An Arrangement does not require at runtime:

```text
Anthimeria
Hipster Stack CLI
Hipster Stack resolver
ownership catalog
pruning rules
generator transforms
hosted Codependent Coding control plane
```

Portable provenance may remain in the repository without becoming runtime dependency.

---

```text
generator metadata          Arrangement
------------------          -----------

portable provenance    →    yes when intentional
```

---

# 6. Architectural Conformance

The generated repository must preserve:

```text
thin App Router boundaries
Feature orchestration
PureUI presentation
BusinessLogic Workflow boundaries
server operation ownership
auth/authz separation
tenant/RLS rules
provider isolation
transaction boundaries
content separation
validation/evidence rules
```

Generation is not permission to flatten architecture simply because unused source has been removed.

---

# 7. Presentation Constitution

The Arrangement contains the presentation selected through Anthimeria/portable config:

```text
route group frame
Page Template topology
Feature Slots
compatible PureUI Blocks
Block variants
Primitive constitution
Primitive variants
Semantic Design Tokens
content/copy
```

Cyan editor slot outlines or other Workbench visualization do not become mandatory runtime styling unless explicitly configured as presentation.

---

# 8. Behavioral Constitution

The Arrangement contains the normalized behavior required by the selected Ontology.

```text
Feature
  ↓
BusinessLogic Block / Workflow
  ↓
architecture-owned constituents
```

Presentation customization does not alter the normalized Workflow semantics.

---

# 9. Provider Readiness

Generated provider code does not prove configured provider readiness.

An Arrangement may require post-generation owner actions such as:

- creating/configuring provider accounts;
- adding environment variables;
- configuring webhook destinations;
- approving migrations;
- provisioning deployment targets;
- defining commercial/provider policy.

The generated app should make these requirements visible.

---

# 10. Provenance

A generated repository may retain:

```text
hipsterstack.json
.hipsterstack/manifest.json
generated README / handoff
```

Useful provenance records:

- generator version/revision;
- Maximal Template revision;
- Virgule/config version;
- selected Ontology;
- resolved capabilities;
- transforms;
- generated artifact set;
- outstanding setup requirements.

Provenance does not replace application governance.

---

# 11. Post-Generation Ownership

After generation, the Arrangement is a normal application repository.

Its owner may:

- develop features;
- commit source;
- run tests;
- deploy;
- maintain migrations;
- use Loaded Vibes or other coding agents.

The application does not remain subordinate to a hosted generator runtime.

---

# 12. Supported Additions

The Hipster Stack may support a bounded `add` operation for known generator-owned optional surfaces.

That does not make the Arrangement a perpetual template clone.

The operation must preserve local ownership and reject incompatible/conflicting state.

---

# 13. Acceptance Conditions

An Arrangement may be called generated when materialization completes.

It may be called acceptance-validated only when required validation actually executes and passes.

Claims should distinguish:

```text
materialized
validated
provider-ready
deployed
```

These are not synonyms.

---

# 14. Canonical Sentence

> **The Arrangement™ is the finished source application, not a generator session. It contains the dependency-complete normalized behavior, configured presentation, required application code, local contracts, tests, configuration examples, and intentional provenance produced from a dependency-closed Virgule and the Maximal Template. It runs independently of Anthimeria and the Hipster Stack runtime.**
